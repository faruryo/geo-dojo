# dashboard Specification

## Purpose
ホーム画面（`app/(app)/page.tsx`）の構成と、その値の定義を保証する。ホームは「おすすめ・復習・制覇進捗」を見せる軽い画面であり、グラフや苦手ランキングなどの詳細な分析は `analytics` に置く。
ホームと詳細分析が共有する集計値（サマリー指標、制覇数）の数え方と、サーバーでの並列プリフェッチ、タイムアウトで初回描画を止めない仕組みもここで定める。連続学習日数は、計算してプリフェッチもするが、現在どの画面も表示していない。
推薦カードの中身は `recommendation`、復習期限と卒業の計算は `srs-review` が正である。制覇の判定と母数の一般的な定義は `municipality-quiz` が正だが、ホームの制覇進捗バーとサマリーの `conquestRateA` は、Mode A のクリアをそれより厳しい定義で数えている（「制覇数と母数の単位」を参照）。

用語: 「県名と同名の市」は、末尾の「市・区・町・村」を除いた名前が、末尾の「都・道・府・県」を除いた県名と一致する市区町村（例: 広島市、京都市）を指す。「複数県にまたがる同名の市」は、同じ名前の市区町村が複数の都道府県にあるもの（例: 伊達市＝北海道・福島県）を指す。

## Requirements
### Requirement: ホーム画面の構成と順序
システムはホーム（`/`）を、上から順に、見出し（「GeoDojo」と「日本地理クイズ」）、推薦ヒーローカード、復習カード、「県当て制覇」の進捗、「場所当て制覇」の進捗の順に表示しなければならない (SHALL)。推薦ヒーローカードの中身は `recommendation` が定め、ここでは配置だけを保証する。復習カードは次の「復習カードの表示条件」に従って出し入れする。

#### Scenario: プレイ履歴がある学習者がホームを開く
- **WHEN** 学習者がホームを開き、累計出題数が1以上である
- **THEN** 見出し、推薦ヒーローカード、復習カード、県当て制覇の進捗、場所当て制覇の進捗が、この順に並ぶ

#### Scenario: 1問も回答していない学習者がホームを開く
- **WHEN** 学習者がホームを開き、サマリーの累計出題数が0と確定している
- **THEN** 復習カードは表示されず、見出し、推薦ヒーローカード、2つの制覇進捗（いずれも 0 件クリア）が表示される

### Requirement: ホームに詳細分析の部品を置かない
システムはホームに、正答率推移、全国制覇推移、難易度別進捗、苦手ランキング、サマリーカードを配置してはならない (MUST NOT)。これらは詳細分析（`/analytics`）が担い、ホームの初回描画を軽く保つ。

#### Scenario: ホームのファーストビュー
- **WHEN** ホームが描画される
- **THEN** 推移グラフ、苦手ランキング、サマリーカードは含まれない

### Requirement: 復習カードの表示条件
システムは復習カードを、サマリーのデータが未取得のとき、またはサマリーの累計出題数が1以上のときに表示しなければならない (SHALL)。未取得には、取得中だけでなく、取得の失敗とオフラインでの一時停止も含まれる。サマリーの累計出題数が0と確定したときだけ、復習カードを表示してはならない (MUST NOT)。復習件数の取得はサマリーの完了を待たず、プリフェッチ済みなら即座に描画する。

#### Scenario: サマリーの取得が終わる前
- **WHEN** サマリーがまだ取得できていない（未定義）
- **THEN** 復習カードは表示対象に含まれる

#### Scenario: サマリーの取得に失敗した
- **WHEN** サマリーの取得が失敗し、データが未定義のままである
- **THEN** 復習カードは表示される

#### Scenario: サマリーが累計出題数 0 を返した
- **WHEN** サマリーの `totalQuestions` が 0 である
- **THEN** 復習カードは表示されない

### Requirement: 復習カードの表示内容
システムは復習カードに、行動ブロック（今日やること）と、状態ブロック（全体の進捗）を表示しなければならない (SHALL)。復習期限の件数、復習中と定着済みの件数、今後7日間の件数の計算は `srs-review` が定める値をそのまま使い、ここでは表示のしかただけを定める。復習件数の取得（`getDueReviewSummary`）と今後の予定の取得（`getUpcomingReviewSchedule`）は、失敗してもリトライしない（`retry: false`）。失敗したときは、件数をすべて0とみなして描画する。つまり復習件数の取得に失敗すると、「今日の復習はありません 🎉」が表示されて状態ブロックは隠れ、復習が0件のときと区別できない。今後の予定だけが失敗したときは、7日分を0件で表示する。
件数はいずれも `srs_records` の行（市区町村コード×モード）の数であり、問題数（1問1件）ではない。Mode A の複数県にまたがる同名の市は、県ごとに別に数える（`srs-review` の「ダッシュボードが使う復習件数と今後の予定」を参照）。

- 行動ブロック: `dueCount` が1以上なら、その件数と「件の復習期日」、および `/quiz/review` へ進む「復習を始める」ボタンを表示する。0なら「今日の復習はありません 🎉」を表示し、`nextDueAt` があれば「次の復習: 今日／明日／N日後」を JST の暦日差で添える（0日以下は「今日」、1日は「明日」、2日以上は「N日後」）。
- 状態ブロック: `reviewingCount + graduatedCount` が1以上のときだけ表示する。「復習中」と「定着済み」の件数、「今後7日間の予定」を表示する。
- 今後7日間の予定: JST の明日から7日分を、予定のない日を0件で埋めて日別の棒で表示する。各棒には件数と `MM-DD` を添え、高さは7日間の最大件数を100%とした比率にする（最大が0のときは最大を1として扱う）。件数が1以上の日の棒には最小の高さを与える。
- 復習中が1件以上のときだけ、`/quiz/review/items` への「覚えている途中の市区町村を見る」リンクを復習中の件数つきで表示する。

#### Scenario: 今日の復習がある
- **WHEN** `dueCount` が 5 である
- **THEN** 「5」と「件の復習期日」が表示され、「復習を始める」を押すと `/quiz/review` へ進む

#### Scenario: 今日の復習がなく、次の期日が明日にある
- **WHEN** `dueCount` が 0 で、`nextDueAt` が JST で翌日の日付である
- **THEN** 「今日の復習はありません 🎉」と「次の復習: 明日」が表示される

#### Scenario: 復習の記録がまだない
- **WHEN** `reviewingCount` と `graduatedCount` がともに 0 である
- **THEN** 状態ブロック（復習中・定着済み・今後7日間の予定・一覧リンク）は表示されない

#### Scenario: 取得中
- **WHEN** 復習件数または今後の予定のどちらかが取得中である
- **THEN** 見出し「復習」とスケルトンが表示される

#### Scenario: 復習件数の取得に失敗した
- **WHEN** 復習件数の取得が失敗する
- **THEN** 「今日の復習はありません 🎉」が表示され、状態ブロックは表示されない

### Requirement: 制覇進捗バー
システムはホームに、県当て（Mode A、見出し「県当て制覇」）と場所当て（Mode D、見出し「場所当て制覇」）の2本の制覇進捗バーを、地方「全国」で表示しなければならない (SHALL)。2本を足し合わせた1本にしてはならない (MUST NOT)。バーの幅は「クリア数 ÷ 母数」を100%で頭打ちにして表すこととし、母数が0のときは0%とする。

- 通常時: 「クリア数 / 母数 クリア」と「あと 母数−クリア数 件」を桁区切りで表示する。
- 全制覇時（クリア数が母数以上で、母数が1以上）: 件数表記に代えて「全市区町村制覇！」を表示する。
- 取得中や未取得の間は、バーの形をしたスケルトンを表示する。

クリア数と母数は、次の「制覇数と母数の単位」で数える。県当て（Mode A）のバーのクリア定義は、`municipality-quiz` の「制覇進捗とその母数」や `recommendation` の制覇率（いずれかのコードを正解すればクリア）より厳しく、両者は一致しない。

#### Scenario: 途中まで制覇している
- **WHEN** 県当てのクリア数が 12、母数が 40 である
- **THEN** 「12 / 40 クリア」と「あと 28 件」が表示され、バーは 30% の幅になる

#### Scenario: 全制覇
- **WHEN** 場所当てのクリア数が母数と等しい（母数は1以上）
- **THEN** 「全市区町村制覇！」が表示され、バーは 100% の幅になる

### Requirement: 制覇数と母数の単位
システムは制覇進捗の値を、モードごとに次の単位で数えなければならない (SHALL)。

- Mode A（県当て）: 名前単位。複数県にまたがる同名の市（伊達市など）は1つの名前として1件に数える。クリアは、その名前の全県のインスタンスが、同じ出題（同じ市名の回答が直前の回答から 2000ms 以内に連なったもの）で全て正解になったときだけ。母数は、県名と同名の市（例: 広島市）と東京23区を除いた名前の数。東京23区は母数にも出題にも含めない。
- Mode D（場所当て）: `municipality_master` のコード単位。政令市の区は区のコードごとに数え、母数は全コードの数（東京23区も含める）。クリアは、そのコードを正解したことがある（`municipality_master` に存在するコードのみ）こと。

地方を指定した場合（ホームは常に「全国」）、Mode A は「その地方に1つでもインスタンスがある名前」、Mode D は「その地方のコード」だけを母数とクリアの対象にする。

#### Scenario: 複数県にまたがる同名の市の1問を全県正解した
- **WHEN** 伊達市（北海道・福島県の2インスタンス）が Mode A で出題され、2県分の回答が2000ms 以内に保存され、両方が正解である
- **THEN** Mode A のクリア数は伊達市で1増える

#### Scenario: 複数県にまたがる同名の市の片方だけ正解した
- **WHEN** 伊達市の2県分の回答のうち片方が不正解である、または1県分しか保存されていない
- **THEN** 伊達市は Mode A のクリアに数えない

#### Scenario: 政令市の区
- **WHEN** 学習者が Mode D で京都市左京区（`26103`）を正解する
- **THEN** Mode D のクリア数は区のコード単位で1増え、京都市という親市単位では数えない

### Requirement: サマリー指標の定義
システムは `getDashboardSummaryData` が返すサマリーを、次のとおり定義しなければならない (SHALL)。ホームは累計出題数が0かどうかの判定に使い、詳細分析がカードとして表示する（`analytics` を参照）。

- `totalQuestions`: 出題の件数。Mode A 以外は保存された行を1問1行で数え、Mode A は同じ市名の回答が直前の回答から 2000ms 以内に連なったものを1問に集約して数える。Mode A の1問は、集約した全行が正解のときだけ正解とする。保存された行数ではなく、この1問1件の数を使う。
- `totalCorrect`: 上の1問1件のうち正解の件数。
- `overallAccuracy`: `totalCorrect ÷ totalQuestions`（0から1の比率。`totalQuestions` が0なら0）。
- `conquestRateA`: 県当て制覇の `coverageRate`（地方「全国」）。`conquestRateD`: 場所当て制覇の `coverageRate`（地方「全国」）。数え方は「制覇数と母数の単位」に従う。
- `prev`: 同じ指標を「当日 JST 0:00 より前（`answeredAt` < JST の当日0:00）」の回答だけで計算した値。制覇率の `prev` も同じ時刻で打ち切る。前日比の矢印の基準となる。

#### Scenario: Mode A の複数県にまたがる同名の市の保存行
- **WHEN** 伊達市の1問が2行（北海道分と福島県分、200ms 差）で保存されている
- **THEN** `totalQuestions` には1問として数え、2行が両方正解のときだけ `totalCorrect` に1を足す

#### Scenario: 今日の回答だけが増えた
- **WHEN** 当日 JST 0:00 以降に回答が追加された
- **THEN** `totalQuestions` は増えるが、`prev.totalQuestions` は変わらない

### Requirement: 連続学習日数の計算
システムは連続学習日数（`getStreakData`）を、その学習者の回答が1件以上ある JST の暦日の集合から計算しなければならない (SHALL)。回答の正誤とモードは問わない。日付の演算はタイムゾーンに依存しない暦日の差で行う。

- `hasPlayedToday`: 最新の回答日が JST の今日であること。
- `currentStreak`: 今日回答していればその日から、今日未回答でも昨日回答していれば昨日から、過去へ連続している暦日の数。今日も昨日も回答していなければ 0。
- `longestStreak`: 全期間で最長の連続日数。常に `currentStreak` 以上になる。
- 回答が1件もなければ、3つとも 0（`hasPlayedToday` は false）。

クイズ中の連続正解数（称賛の段階、`lib/quiz/streak.ts`）は別のもので、ここには含めない。

この値はホームと詳細分析のサーバープリフェッチで取得されるが、現在どの画面にも表示されない。表示する部品（`StreakDisplay`）はどこにも配置されていない。

#### Scenario: 今日未回答で昨日まで続いている
- **WHEN** 回答日が昨日、一昨日、その前日である（今日はない）
- **THEN** `currentStreak` は 3、`hasPlayedToday` は false になる

#### Scenario: 一昨日が最後
- **WHEN** 最新の回答日が一昨日である
- **THEN** `currentStreak` は 0 で、`longestStreak` は過去の最長連続日数のまま残る

#### Scenario: 日付の境界は JST
- **WHEN** UTC の D日 15:00 以降（JST の D+1日 0:00 以降）に回答した
- **THEN** その回答は JST の D+1日の回答として数える

### Requirement: ホームの初回プリフェッチ
システムはホームの描画前に、サーバーで、読み取りごとではなく1回の `getUser()` でユーザーを解決したあと、ファーストビュー向けの読み取りを並列にプリフェッチして dehydrate し、`HydrationBoundary` でクライアントへ渡さなければならない (SHALL)。対象は、サマリー、連続学習日数、復習件数サマリー、今後7日間の復習予定の4つである。連続学習日数はホームに表示されないが、取得している（「連続学習日数の計算」を参照）。推薦ヒーローカードと制覇進捗バーは対象に含めてはならない (MUST NOT)。プリフェッチ用の `QueryClient` はリクエストごとに新しく作る。未認証（ユーザーID が取れない）のときは、何もプリフェッチせずに状態なしで描画する。

dashboard 系のクエリキー（`['dashboard', …]`）にはユーザーIDが入っておらず、ログイン状態が変わっても破棄されない。これが許される理由は `auth` の「ブラウザ側のユーザー ID」を参照。

#### Scenario: 認証済みの通常表示
- **WHEN** 認証済みの学習者がホームを開く
- **THEN** サマリー、連続学習日数、復習件数サマリー、今後7日間の復習予定が同じ HTML の初回描画に載り、クライアントは同じキーの再取得を待たずに描画できる

#### Scenario: 制覇進捗バーと推薦ヒーローカードはプリフェッチされない
- **WHEN** ホームの初回描画が返る
- **THEN** 制覇進捗バーと推薦ヒーローカードはクライアント側の取得を待ち、制覇進捗バーは取得が終わるまでスケルトンを表示する

### Requirement: プリフェッチのタイムアウトと失敗時の退避
システムは、認証のあとのデータ読み取りの待ち時間を `PREFETCH_TIMEOUT_MS`（2,000ms）で打ち切らなければならない (SHALL)。認証確認（`getUser()`）はこの打ち切りの対象外で、その前に完了を待つ。2,000ms を超えたとき、またはプリフェッチ全体が例外で失敗したときは、部分的な結果を渡さずに dehydrate の結果を `null` にし、画面は状態なしで描画してクライアント取得にフォールバックする。ただし `prefetchQuery` は個別の失敗で reject しないため、「全体が例外で失敗」する経路には実際にはほぼ入らない。待ち時間用のタイマーは完了後に必ず解除する。打ち切っても、サーバーで走っている読み取りは中断されずに最後まで続き、その間 DB 接続を使い続ける。このため、クライアント側の再取得と同時に接続を使うことになる。

サーバーの `QueryClient` は `retry: 1` で作られる。このため、個別のクエリが失敗すると、既定のバックオフ（約1秒）を待ってもう1回だけ実行される。リトライでも失敗したクエリは dehydrate に含めず、クライアントがそのクエリだけを取得し直す。リトライの待ちで全体が 2,000ms を超えた場合は、ほかの成功したクエリも含めて全体が `null` になる。

2,000ms という値は、ファーストビューの並列読み取りの実測最遅を超え、かつ旧来の 8 秒待ちより十分短くなければならない。

#### Scenario: プリフェッチが 2,000ms 以内に終わる
- **WHEN** 全てのプリフェッチが 2,000ms 以内に完了する
- **THEN** 取得済みのデータが dehydrate されてクライアントへ渡る

#### Scenario: プリフェッチが詰まる
- **WHEN** いずれかの読み取りが 2,000ms を過ぎても終わらない
- **THEN** 初回描画は待たされずに返り、クライアントが各データを取得して描画する

#### Scenario: 1つの読み取りが失敗する
- **WHEN** 4つのうち1つの読み取りが失敗し、リトライを含めても全体が 2,000ms 以内に終わる
- **THEN** 成功した3つは dehydrate されて渡り、失敗した1つだけをクライアントが取得し直す

### Requirement: 認証確認と DB 接続プールの上限
システムはサーバーでの認証確認を、`getUser()` の直呼びで行わなければならない (SHALL)。`getClaims()` を使ってはならない (MUST NOT)。現行の構成（対称鍵・JWT 署名鍵未設定）では `getClaims()` が内部で `getSession()` と `getUser()` を入れ子に呼んでロックを取り合い、認証後の SSR が数分間ハングしたためである。`/` と `/analytics` の1リクエストでは、`getUser()` が2回呼ばれる。1回目は `app/(app)/layout.tsx` の認証ガード、2回目はページのプリフェッチで、両者の結果は共有されない。認証確認にはタイムアウトがない。ハングしないことの保証は、`getClaims()` を使わないことだけに依る（`auth` の「サーバー側のユーザー解決」も参照）。

サーバーの DB 接続プールは同時 20 接続（`max: 20`）とし、サーバー側プリフェッチの並列読み取りが既定の10接続を使い切って詰まることを避けなければならない (SHALL)。各読み取りは内部でもサブクエリを並列に発行する。ピーク時の同時発行数は、ホームで約23本（サマリーだけで約17本）、詳細分析で約29本で、20 でも超過分は待ち行列に入る。

#### Scenario: 認証後のホーム描画
- **WHEN** 認証済みの学習者がホームを開く
- **THEN** 認証確認は `getClaims()` を使わずに `getUser()` で行われ（レイアウトとプリフェッチで計2回）、ロックの取り合いによるハングが起きない

#### Scenario: 並列プリフェッチ中の接続
- **WHEN** ホームのプリフェッチが複数の読み取りを同時に発行する
- **THEN** 接続プールは同時に最大20接続まで使い、ピーク時の超過分（ホームで約3本）は待ち行列に入る
